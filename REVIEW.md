# Workout Logger Review

Reviewed raw commit `018572d` against `SPEC.md`. The Expo Router screens, validation, date handling, and history ordering satisfy criteria 1–4 by code inspection. The persistence implementation supports criterion 5, which still needs an Expo Go cold-restart test. No blocking defect was found on the specified save path.

## Acceptance criteria

1. **[PASS] Workout History opens with the specified empty message.** The root layout registers the `index` screen as “Workout History” (`src/app/_layout.tsx:17`). A missing storage key becomes an empty array (`src/workouts/storage.tsx:26–33`), and the list renders “No workouts before.” once the read succeeds (`src/app/index.tsx:20–35`).
2. **[PASS] Add Exercise opens Log Exercise with the three requested fields.** The history button links to `/log` (`src/app/index.tsx:25–30`), the stack titles that route “Log Exercise” (`src/app/_layout.tsx:18`), and the screen provides exercise name, weight in pounds, and sets (`src/app/log.tsx:62–98`).
3. **[PASS] Zero weight is valid, and blanks or zero sets cannot create an entry.** The form trims the name and checks weight syntax before allowing the numeric value. The weight check accepts `0` and rejects blank input. Sets must be a positive safe integer. Every invalid case returns before the save call (`src/app/log.tsx:18–47`).
4. **[PASS] A valid save records the local date, returns to history, and shows the new entry first.** The handler builds the date from the device's local calendar and returns to `/` after the write resolves (`src/app/log.tsx:38–52`). Storage inserts the new entry at the front and publishes the updated list (`src/workouts/storage.tsx:56–69`). History renders the date, name, weight, and sets in stored order (`src/app/index.tsx:8–12`, `src/app/index.tsx:21–43`).
5. **[WARN] The cold-restart persistence path is present and awaits device verification.** The provider awaits an AsyncStorage write before updating history (`src/workouts/storage.tsx:60–69`), and the root provider reloads the same key on mount (`src/workouts/storage.tsx:10`, `src/workouts/storage.tsx:26–49`, `src/app/_layout.tsx:7–20`). The declared AsyncStorage version matches the installed Expo SDK's bundled module list (`package.json:7–8`, `node_modules/expo/bundledNativeModules.json:7`). Completion of the full save, force-close, and reopen sequence in Expo Go remains unverified.

## Additional findings

6. **[WARN] A pending save can navigate after the user leaves the form.** Save disables the form controls, while the stack's back action remains available. If the user backs out during a slow write and opens a fresh form, completion of the original save can dismiss the new form and discard its draft. The write should be allowed to finish, with post-save navigation guarded by the original screen's focus or with back navigation disabled during the write (`src/app/log.tsx:43–56`, `src/app/log.tsx:104–111`, `src/app/_layout.tsx:11–18`).
7. **[WARN] An unreadable stored payload leaves history and exercise entry unavailable.** A malformed payload or one invalid row turns the whole read into an error. The history screen offers a retry, which reads the same payload again. This handles transient read failures and leaves persistent corruption without a recovery path. Distinguish read failures from invalid data and provide a recovery path that preserves recoverable entries (`src/workouts/storage.tsx:17–36`, `src/workouts/storage.tsx:51–54`, `src/app/index.tsx:47–58`).
8. **[WARN] Stored date and ID checks can admit inconsistent rows.** A date such as `2026-02-31` passes the regex and displays as a date in March. Duplicate IDs pass validation and become duplicate React list keys. IDs derived from array length may also collide if imported or recovered entries omit earlier rows. These cases require data outside the current form's normal save path (`src/workouts/storage.tsx:17–33`, `src/workouts/storage.tsx:62–66`, `src/app/index.tsx:8–12`, `src/app/index.tsx:23–24`).
9. **[PASS] The normal save path handles write failures and repeated taps.** The form uses a synchronous guard against repeat submission, identifies the pending state to assistive technology, and allows retry after failure. The provider changes the in-memory list only after the write resolves and releases its write lock in `finally` (`src/app/log.tsx:14–19`, `src/app/log.tsx:43–53`, `src/app/log.tsx:100–111`, `src/workouts/storage.tsx:56–70`). The history uses a virtualized list, and the form uses safe-area handling, keyboard-aware scrolling, labeled fields, and numeric keyboards (`src/app/index.tsx:18–24`, `src/app/log.tsx:58–98`).
